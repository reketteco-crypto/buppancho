# フェーズ0 設計判断

- **共通ログインと入力者を分離する:** 共通アカウントを使い、初期設定で登録した任意の入力者をセッション上で選ぶ。監査上は自己申告であることを常時表示する。
- **独自のDBセッションを使う:** 外部認証サービスへ依存せず、失効、期限、入力者・部門・年度をサーバー側で検証できるようにする。Cookieには不透明トークン、DBにはSHA-256ハッシュだけを保存する。
- **初期アカウントはCLIで作る:** 未認証の初回セットアップ画面を外部へ公開しない。パスワードはTTYで非表示入力し、引数・環境変数・履歴へ残さない。
- **初期構成を編集可能にする:** ユーザー要件を基準仕様の固定初期データより優先し、「事業主」「アパレル担当」「中国輸入」「アパレル」を編集可能な初期値として提示する。申告主体は事業主1件、両部門の帰属は事業主を初期値とするが、アプリは税務判断を行わない。
- **年度別に担当と帰属を保持する:** 主な入力者と申告主体は販売部門の年度別割当に保持し、翌年度コピー後の変更が過去年度へ影響しないようにする。
- **期間重複をDBで拒否する:** 年度別割当はPostgreSQLの排他制約で守り、アプリ側検証だけに依存しない。
- **設定を物理削除しない:** フェーズ0のマスターは`active`で無効化し、更新前後を監査ログへ残す。認証スロットル等の一時データだけは削除可能とする。
- **PWAは静的外枠だけを保持する:** 認証済み業務データや更新要求をキャッシュせず、オフライン時は案内画面へ退避する。自動再送は行わない。
- **金額型をまだ導入しない:** フェーズ0に金額データはない。後続フェーズでは整数円またはPrisma Decimalを使い、JavaScript `number`で金額を計算しない。
- **PostgreSQL 18の配置へ合わせる:** 公式イメージ18系のバージョン別`PGDATA`に合わせ、永続ボリュームは`/var/lib/postgresql`へマウントする。
- **バックアップ状態をDB外へ記録する:** DB停止による失敗も表示できるよう、共有ステータスJSONを正とする。復元は空DBだけを許可する。
- **Cloudflareは任意profileに留める:** フェーズ0ではトンネル作成・外部公開を行わず、将来HTTPSとAccessを設定できるCompose構造だけを用意する。

# フェーズ1 設計判断

- **数量商品の管理原価は移動平均法に限定する:** FIFOは将来拡張用のenumだけ保持し、フェーズ1の登録画面では選択不可とする。税務上の棚卸評価方法とは分離する。
- **国内仕入れは一括入庫とする:** 分納・一部入庫はRakumartを扱うフェーズ3で共通処理として追加する。
- **コードは自動採番し編集を許可する:** 商品は`ITEM-000001`、個体は`UNIT-000001`、仕入は`PUR-000001`形式とし、採番済み番号は再利用しない。
- **商品状態と在庫追跡を分離する:** 新品・中古は仕入明細の実績値、数量管理・個体管理は在庫追跡方式として別に保持する。商品マスターの値は仕入入力時の既定値に限る。
- **国内仕入れの入口を統合する:** 1件の仕入れで数量管理明細と個体管理明細を混在可能とし、利用者向けの開始方法は「新品・同一商品」「中古・一点物」とする。
- **バリアントコードはワークスペース一意とする:** バリアントは自由な属性名・値の直積から生成でき、`VAR-000001`形式の採番または保存前の編集を許可する。
- **在庫移動履歴を正とする:** 原価残高、ロット残数量、個体の現在場所・状態は検索用キャッシュとして同じトランザクションで更新し、履歴と照合可能にする。
- **数量払出しのロット帰属と原価方式を分ける:** 数量は古いロットから順に減らして追跡可能にするが、払出原価はロット原価ではなく移動平均原価を使う。
- **部門間移動はフェーズ1対象外とする:** 同一部門内の場所移動と調整だけを扱い、部門間の所有・会計処理が確定してから追加する。
- **確定仕入れの取消条件を厳格にする:** 対象ロットが全量残り、入庫後の移動や状態変更がない場合だけ反対移動を作成する。
- **円金額はbigintで保持する:** Server Action境界では整数文字列、DBでは`bigint`、平均単価計算ではDecimalを使い、監査JSONでも文字列化する。
