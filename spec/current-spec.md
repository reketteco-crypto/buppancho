# 物販帳（Buppancho）現行仕様

文書版：3.2。更新日：2026-11-25。

本書を業務仕様の唯一の正本とする。実装・検証の到達点と未確認事項は [検証状況](../docs/validation.md)、開発上の制約は [開発規約](../AGENTS.md) に記載する。要件として記載されていることと、実装・検証が完了していることを区別する。

## 1. 目的と範囲（SCOPE）

購入・受取・在庫・販売・費用・入出金を一元管理する、日本語のWebアプリとする。商品カテゴリ・取引先・販路に固有の業務モードは設けず、共通の購入明細、配送、受取、管理方式、費用配分で表現する。

対象は数量商品、1点もの、セットSKU、資材・備品、外貨購入、同梱・分割配送、分割受取、返品・返金、原価訂正、通常口座・カード・本人立替、管理利益と円建て残高である。

税務判定、複式簿記、自動仕訳、申告用集計、他の会計ソフトからの移行は対象外とする。税務上の帰属や費用処理を推測して決定しない。

販売は取引完了時に1回入力する。出品登録・在庫確保・購入成立・発送の入力を要求せず、それらの架空のイベントも生成しない。販路の出品数・出品状態は管理しない。

## 2. 入力先・年度・初期設定（CTX）

### 2.1 入力先

- ワークスペース：認証とデータ分離の最上位領域。
- 入力者：実際に入力を担当した人。共通ログインの場合は自己申告であることを表示する。
- 販売部門：活動・在庫・収支を管理する単位。
- 申告主体：部門の年度別割当に基づく帰属先。入力者と区別する。
- 対象年度：出来事の日付、年度設定、ロック状態を検証する単位。

すべての読み書きで認証とワークスペースを確認する。部門・申告主体・年度を持つデータはその帰属で限定し、任意のIDだけで別の入力先へアクセスさせない。表示名・候補検索・件数・ページ位置の取得にも同じ境界を適用する。

### 2.2 初期値

| 種類       | 編集可能な初期値                 |
| ---------- | -------------------------------- |
| 入力者     | 事業主、アパレル担当             |
| 販売部門   | 中国輸入、アパレル               |
| 申告主体   | 事業主1件                        |
| 部門の帰属 | 両部門とも事業主の年度設定へ割当 |

初期値は固定の業務モードや税務判断を意味しない。必要に応じて追加・編集でき、複数の申告主体にも対応する。

### 2.3 年度と版

- 年度別割当は期間の重複を拒否し、翌年度の設定変更で過去年度を変更しない。
- 入力開始時の帰属を保持し、再開時に現在設定へ黙って付け替えない。
- 出来事日は日本時間、記録日時はUTCとする。不明な日付を作らない。
- 対象年度が異なるときは入力内容を保持して明示的に切り替える。切替だけで業務を確定しない。
- ロック年度の業務更新・確定原価変更を拒否する。保存済み要求の結果照会は、要求への権限を再確認した上で可能とする。
- 設定とマスターは表示時の版を更新時に確認する。古いフォームを無条件に上書きせず、手元入力を保持する。

## 3. 画面と共通操作（UI）

主要入口はホーム・購入・商品・販売・お金の5つとし、設定は独立させる。

| 入口   | 主な役割                                                       |
| ------ | -------------------------------------------------------------- |
| ホーム | 要確認、途中入力への復帰、管理状況の確認                       |
| 購入   | 購入入力、配送・受取、費用・返金・返送                         |
| 商品   | 在庫商品、単品・セットSKU、資材・備品                          |
| 販売   | 完了した販売の記録と、返品・費用・入金の追加                   |
| お金   | 口座残高、カード、本人立替、入出金履歴、その他の費用・収入     |
| 設定   | 入力先、年度、取引先、保管場所、販路、配送方法、口座、収支項目 |

- 通常入力は一画面で行い、例外と詳細は必要時に展開する。
- 見出しと操作群を分け、操作間は原則12px空けて折り返す。チェック記号は18〜20px、ラベルを含む操作領域は44px以上とする。PCの現在地と詳細からの戻り先を示す。
- 補足は選択内容に応じて表示し、詳しい説明はタッチ・キーボードでも展開できる。必須条件、未確認値、エラー、在庫・原価への影響は隠さない。エラーから該当欄を開きフォーカスできるようにする。
- 商品・口座などの選択は検索でき、検索条件にかかわらず選択済みの値を保持する。UIでは「販売する商品」を主表示とし、SKUやセット構成の説明を必要時に表示する。
- 購入・通常販売・販売まとめ入力は入力停止後900msを基本に自動で途中保存し、保存中・保存済み・確認できない状態を示す。販売・入庫・決済の確定は明示操作だけで行う。
- 入力中のアプリ内移動・入力先変更では、元の入力先への途中保存を確認してから移る。保存成功後の復帰は離脱防止で止めず、競合・結果不明では確定を再実行しない。
- ホームの再開一覧は帰属・入力者・年度内の下書きだけを要約し、販売まとめ入力はファイル名と全件・入力途中・保存済み件数を示す。確定済み・対象外だけのまとめ入力と内部確認・対応記憶は再開一覧へ混ぜない。
- お金の入口は売上入金・仕入支払・その他の経費／収入・口座間移動・立替精算の目的を区別する。設定は日常入力、事業・年度、運用にまとめて用途を示す。
- PC・スマホ幅に対応し、操作領域は原則44px以上、入力欄は16px以上とする。
- ラベル、キーボード操作、フォーカス移動、日本語のエラーと修正方法を用意する。色だけで状態を示さない。
- 検索・絞り込み・ページはURLへ保持し、位置・選択状態は入力先に応じて分離する。
- 販売一覧は申告主体・検索・年度／月・訂正反映後の有効日で絞り込み、安定した順序で50件ずつ表示する。上下に件数・前後ページ操作を置き、詳細から同じ条件・ページ・位置へ戻れるようにする。
- 設定へ移る場合は最新入力の下書き保存を確認し、同じ入力へ戻れるようにする。ブラウザへ業務データを永続保存しない。
- フォームは操作イベントの接続後に入力可能にする。初期表示直後の操作を保存時の初期値で上書きしない。
- 通常販売30秒以内、通常経費20秒以内を人の入力時間の目標とする。自動試験の実行時間と区別する。

## 4. 購入（PUR）

### 4.1 共通購入入力

- 購入日、取引先、注文番号、通貨、換算根拠、税込／税抜、税額、明細、費用、メモを扱う。
- 数量商品・1点もの・資材・備品を同じ購入に混在させる。在庫商品の管理方式は数量管理または個体管理、資材・備品は在庫管理なしとする。
- 明細金額は単価入力または明細合計入力とし、数量と区別する。
- 商品代金の通貨・換算を商品明細の直前へ配置し、外貨の初期表示・ファイル反映時は入力欄を開く。商品代金用のレートと費用ごとのレートを見出し・項目名で区別する。
- 数量・単価・円換算条件が不足すると「計算待ち」と理由を表示し、必要な欄へ移動できる。必要条件がそろうと自動で円金額を表示する。未入力費用がある合計は暫定とし、金額がそろって配分だけが不足する場合は「原価の配分待ち」とする。
- 購入合計の直前に数量管理商品の「商品ごとの原価」を表示する。費用配分までそろったら、今回の仕入原価／個と補充後の平均原価／個、既存在庫の平均原価の変更前後を示す。内訳は今回・既存・補充後の数量と原価合計を表示する。
- 受取済みの補充後平均は、共通原価プレビューの入庫直前・直後の残高を使い、日付と同日の記録順序に従う。未受取は現在の帳簿在庫に今回分を加えた参考値とし、実際の平均原価は受取時に決まると示す。
- 同じ商品IDの複数明細は補充後の計算で合算し、今回の単価は明細ごとに表示する。新規と在庫0は今回原価を平均とし、原価が暫定の在庫を含む場合は「暫定」を付ける。不整合・取得失敗は「要確認」として再取得できる。
- 原価表示は入力変更後500msで再計算し、古い応答を破棄する。単価は小数第2位まで表示し、丸めがある場合は「約」を付ける。保存時の原価確認と版検証で再評価する。
- 未受取の購入を保存できる。受取済みなら入庫を同時に行い、支払も任意で同時保存できる。
- 支払の初期値は未払い。口座・カード・本人立替を選んだ場合は日付・金額・口座・版を検証する。
- 購入・受取・任意支払は同一トランザクションとし、一部だけ確定しない。
- 連続入力では取引先・通貨を引き継げるが、前の金額・数量・商品ID・支払を別取引へ黙ってコピーしない。
- 購入・取引先の保存済み名称を保持し、マスター名称の変更で過去表示を置き換えない。

### 4.2 費用配分・外貨

- 費用ごとに名称、金額、通貨、換算、原価算入、対象明細、配分方法を保存する。
- 配分方法は商品金額比を初期値とし、数量・重量・容積・明細均等・手動を選べる。配送方法から配分方式を強制しない。
- 手動配分は整数円の金額とし、合計が元費用と一致しなければ確定しない。
- 円端数は最大剰余法で配り、同率時は固定明細順とする。
- 配分基準が不足する場合は配分待ちとし、不明金額を0円として確定しない。
- 外貨・為替・換算・配分はDecimalで計算する。実支払円額による補正の根拠を保存する。
- 商品代金と同じ通貨の費用は、費用側のレートが未入力なら商品代金のレートを使用すると表示する。費用側へ入力したレートはその費用の換算に使う。購入全体の円建て実額は商品代金と費用を含む実額として入力する。
- 費用訂正・値引き・返金は元費用を保持して関連付け、影響する在庫原価・販売原価を確認してから追記する。

### 4.3 配送・受取

- 配送と受取を支払から分離し、同梱・分割配送・分割受取を扱う。
- 配送費はその配送に対応する受取数量へ配分する。
- 後日入力した配送と受取の対応は追記する。元の受取・移動・消費を上書きしない。
- 購入・配送より前の受取、受取より前の現物返送など、日付の矛盾を拒否する。
- 非在庫明細に在庫ロット・個体・在庫移動を作らない。

### 4.4 商品・購入履歴から選ぶ

- 商品名の近くに「商品・履歴から選ぶ」を置く。登録商品・購入履歴を検索し、各50件で表示する。
- 選択では商品ID・表示名・1個の重量・容積を反映する。入力済みの単価・明細金額・数量・金額入力方式・通貨・換算・費用・支払を保持する。
- 管理方法が一致する有効商品を候補にする。管理方法の切替は利用者の明示入力で行う。
- 取込元名称を `purchase_document_line.source_name`、統一後の名称を `name` として併存させ、詳細・検索・書類照合へ使う。
- 重量・容積は商品IDを基準に、購入日以前の同じワークスペース・部門・申告主体の有効記録から、それぞれ最新の正の値を候補にする。名称だけで自動対応付けしない。
- 取消購入と訂正前の費用根拠を除外し、日付・記録日時・IDの降順で候補を選ぶ。参照日・購入番号を表示する。
- 入力後は今回の保存値として固定する。日付や過去履歴の変更で入力済み値を再補完しない。候補がなければ空欄を保つ。
- 配送・追加費用の計量欄は対象明細自身の計算根拠を優先し、不足だけを履歴から補完する。費用訂正は元費用の根拠を引き継ぐ。
- 検索エラーの再試行、古い検索応答の破棄、キーボードでの選択に対応する。

### 4.5 ファイル取込と費用の表示

- Excel・PDFを端末内で共通入力候補へ変換する。取引先固有の書式判定は取込アダプターへ限定し、共通の原価・在庫・決済処理へ持ち込まない。
- 読み取れない項目は未解決として表示する。候補確認・入力欄への反映・利用者による保存を分ける。
- 費用ごとに名前付きの枠を置き、金額・通貨換算・配分・対象・削除をまとめる。削除対象を読み上げでも識別できるようにする。
- 購入入力の送料・税額ファイルは購入全体の費用に追加する。配送単位の費用は購入保存後の配送入力・配送詳細から追加する。この違いを候補確認時に表示する。
- 購入・配送詳細からファイル取込を明示的に開けるようにする。既存の手入力を保持して候補を追加する。
- 配送書類は保存済み注文番号、表示名・元名称を照合する。曖昧な対応は利用者が選ぶ。
- Rakumartの配送依頼書詳細は国際運賃を費用候補にする。注文書で記録する代行手数料が配送書類に再掲されるため、配送書類の代行手数料を取込対象から除外する。
- 別の費用の通貨換算・手動配分を新しい費用へ黙ってコピーしない。

### 4.6 誤登録取消と実際の返送

- 誤登録取消は未使用・未決済・配送なし等の条件を確認し、元の入庫を保持して反対入庫を作る。取消理由と日付を保存し、取消後の詳細を読み取り専用にする。
- 実際の返送、値引き、返金は元購入に紐づく別の記録とする。受取数量・既存返送数量・有効原価を検証する。
- 元取引の金額訂正、過払返金、不足支払の関係を追跡し、返金と決済を重複させない。

## 5. 商品・SKU・一覧（CAT）

- 在庫商品は数量管理と個体管理を分ける。新品・中古という状態から管理方式や原価方式を決めない。
- 商品・バリアント・個体コードを区別する。商品コードは新規作成時だけ編集でき、登録後は変更しない。採番済み番号を再利用しない。
- SKUは単品または在庫商品の組合せとする。SKU作成だけでは在庫を減らさず、循環構成を認めない。
- 単品SKUの一括登録とセット作成を分ける。受取済み購入では任意で単品SKUを同時作成し、既存の単品SKUを再利用する。資材・備品をこの操作の対象にしない。
- 販路別の価格・手数料候補・配送方法・送料、資材の用途・使用量・指定単価を設定する。販路条件を推測で設定しない。
- 在庫商品・SKU・資材／備品を各50件で表示し、上下に件数とページ操作を置く。
- 一括SKU登録は最大200件。検索・ページをまたぐ選択を保持し、保存時に全件を再検証する。利用不可対象があれば全件を保存しない。
- 商品名は詳細への操作、チェックボックスは選択の操作とする。選択中の一括操作はスクロールしても利用できるようにする。
- 詳細・編集から元の検索・ページ・位置へ戻り、選択を保持する。タブ・入力先の変更で選択を解除する。
- 商品は名称・分類・メモ・既定保管場所・有効状態、資材／備品は名称・メモ・有効状態を版付きで編集する。
- 数量・原価・コード・管理方式・数量の意味を変える単位や用途を通常編集で変更しない。購入・販売・資材使用に保存した名称と原価を保持する。

## 6. 在庫・原価・日付訂正（STK）

### 6.1 在庫の記録

- 在庫移動の履歴を正とし、残数量・原価残高・個体の場所と状態は同じトランザクションで更新する。
- 数量商品の管理原価は移動平均法、個体は個別法とする。数量払出しのロット帰属順と原価計算方式を区別する。
- 同じ個体の二重販売と、利用可能数を超える消費を拒否する。資材・備品の残数は管理しない。
- 場所移動・廃棄・紛失・私用・数量調整は理由と数量を記録する。販売の代わりに在庫調整を使わない。
- 数量実測は実測日時・場所の帳簿数との差を固定保存する。遡及入力があっても実測値・調整数量を自動変更しない。差0では架空の移動を作らない。

### 6.2 後日入力・原価の訂正

- 出来事順に入庫・払出し・返品を確認し、必要な原価を計算する。同日の順序で原価・在庫成立性が変わる場合だけ前後を選択する。
- 計算順序と実際の時刻を分け、便宜的な時刻を捏造しない。
- 今回の原価・利益、影響する既存取引、在庫原価残高の変更前後と暫定状態を確認してから確定する。
- 履歴不足、途中時点の在庫不足、入庫前の払出し、帰属の不一致、ロック済み原価の変更を拒否する。不明を0円や現在原価で埋めない。
- 元の移動・消費を上書きせず、原因・変更前後を持つ原価訂正を追記する。今回の出庫は1回だけとし、既存数量を再生成しない。
- 確認した入力・版と確定時の在庫・年度・取引を再照合する。条件が変われば再確認を求める。

### 6.3 日付訂正

- 購入・受取・販売完了・現物返送／返品の訂正は理由と元日付を保持し、有効日を在庫・原価・精算・表示へ反映する。
- 同じ未ロック年度内で整合性と影響を確認して記録する。元の移動と日付を上書きしない。
- 購入・配送・受取・販売・返品の前後関係や、資材追加使用との矛盾を拒否する。
- 確定前の未送信入力を、ブラウザ破棄後まで復元できるとは保証しない。

## 7. 販売・返品（SALE）

### 7.1 完了時の販売入力

- SKU・販路・数量・完了日・実売金額を確認して保存する。数量は1、日付は日本時間当日を初期値とする。商品ID・購入者は任意。
- 販路・SKUの候補から価格・費用・配送方法・資材を補完し、利用者が確認する。
- 手入力した価格・手数料・送料・配送方法と、再開した下書きの値は、商品・販路の変更で置き換えない。設定値への置換は明示操作とし、未確認と0円を区別する。商品変更時はその商品の構成・資材候補を再確認する。
- 在庫商品の構成・消費数量・名称・使用原価、資材の使用量・単価、受取口座・差引方法を販売時に固定する。
- 販売実績・出庫・原価・資材使用・保存結果・監査を単一トランザクションで記録する。
- 完了記録の再送や並行確定で二重出庫しない。連続入力では販路を引き継げるが、前の価格・商品ID・購入者を別取引へコピーしない。

### 7.1.1 販売のまとめて入力

- 販売一覧からまとめ入力を開き、「ファイルから追加」と複数行の手入力を同じ画面で扱う。形式判定と特定販路の列変換は取込アダプターに限定し、現在の対応形式がメルカリ販売CSVであることを示す。
- 取込は5,000行・8MB以内とし、50行ずつ表示する。検索・期間・ページをまたいで編集内容と選択を保持する。期間は完了日で絞り込み、未入力行に購入日を代用しない。
- PCは選択・商品・完了日・数量・金額・状態を一覧内で編集し、販路・費用・元データ等は行内で展開する。1280×800で基本行を少なくとも6件表示する。スマホは商品概要から必要な行を開き、画面全体を横スクロールさせない。
- 入力不足・要確認・確認済み・未評価・保存済み・対象外を区別する。行の選択と取引完了の確認を分け、一括設定は対象件数と変更範囲を示す。
- 初回の途中保存は全体を送信し、以後は行IDごとの変更行を送信する。正確な元版にだけ適用して全体を再検証し、同キーの再送は同結果、別内容・古い版は拒否する。結果不明では同じ要求内容の確認を先に行い、確定済み行を変更しない。
- 元の商品名・購入日時・更新日時・ファイル名・参照URL・商品原価控除前の販売利益を保持する。商品代金・手数料・送料をSKUや配送方法の既定値で上書きしない。
- CSVの商品代金は取引全体の金額として扱い、手入力は単価と取引全体の金額を選べる。全体金額がSKU販売数で割り切れない場合は丸めず、販売単位に対応するセットSKUと数量1での入力を求める。
- SKU・販路・数量・完了日・配送方法・手数料・送料・完了済み確認を個別または選択行へ設定できる。セット内の消費数はSKU構成を使い、名称の枚数表記から推測しない。私物等は対象外にできる。
- 確認した商品名とSKUの対応を部門・申告主体・販路ごとに記憶する。同じ元名称への候補反映は明示操作とし、SKUが未指定の選択行だけへ反映する。
- 新規CSV読込時は有効な更新日時の日本時間の日付を完了日の初期値とする。タイムゾーンのない日時は日本時間として扱い、不正日付は空欄とする。購入日時は代用せず、取引完了の確認も自動で付けない。既存下書きの日付は自動変更せず、空欄への更新日反映は明示操作だけで行う。
- 未確認の完了日・取引状態、仕入・入庫不足の行も途中保存できる。不足を補完するまで販売を確定しない。ホームからまとめ入力を再開でき、購入・受取を別画面で登録した後も元の下書きで再確認できる。
- 選択行を完了日順、同日は入力行順に仮反映し、商品原価・資材原価・利益・在庫残高と既存販売への影響をまとめて示す。同日の既存履歴との順序で結果が変わる場合は選択を求める。先行行の確認事項で後続の計算を止め、補完・対象選択の変更後に全選択行を再確認する。
- 計算は入力した順ではなく有効な入庫・販売等の出来事順で行う。後から販売日以前の入庫を追加した場合は、その購入・受取の原価確認で既存販売等への変更を示し、6.2の訂正履歴を追記する。販売数量を再出庫しない。未保存の一括確認は失効させる。
- 確認後は1行ずつ独立したトランザクションで販売・出庫・原価・監査・保存結果を確定する。確認済みの順序と影響を検証し、先行行の保存による予定どおりの変化だけを引き継ぐ。外部更新、競合、失敗、結果不明で後続を停止し、保存済み行を保持する。
- 元要求の照会・取消を業務更新から分離し、通信復帰や再開で自動確定しない。途中保存の競合では元基準・手元入力・理由を退避した新下書きだけを作り、自動マージしない。確定済み行を通常編集しない。
- 商品IDの既存重複と同じ取込内の重複を検出し、行ごとの冪等キーで二重出庫を防ぐ。今回のまとめ入力から入金記録は作らない。未確認費用・暫定原価を含む利益は未確認とする。

### 7.2 未確認費用と後日の補完

- 手数料・送料等は確認額、明示的な0円、未確認を区別する。見込み候補を実費へ自動確定しない。
- 費用未確認でも販売を記録できるが、要確認を残す。情報が不足する利益を確定値として表示しない。
- 後日の金額補完・再送料・追加費用は理由と差分を保存する。在庫へ再作用しない。
- 未確認費用が受取額を左右する場合は決済を保留する。

### 7.3 返品・返金

- 現物返品と在庫を動かさない返金を区別し、元販売に紐づけて追記する。
- 売上返金、手数料返還、送料返還は別々に確認する。未確認は途中保存までとし、現物返品・在庫も確定しない。
- 構成品・数量別に良品・不良・廃棄を記録し、良品だけを販売可能在庫へ戻す。
- 累計数量は元消費数量、累計戻し原価は訂正反映後の元原価を上限とする。最後の数量で残る原価端数を吸収する。
- 販売単位数に架空の分数を作らない。構成品別処理後の残りは構成品数量で扱い、販売単位全体として重複処理しない。
- 返金のみは理由と正の返金・返還額を1つ以上必要とする。
- 後日返品は共通原価確認を行い、原価・利益・在庫への影響を確認する。年度・帰属・数量・金額の上限と確定時の版を再検証する。
- 競合時に他端末の返品をコピーしたり、数量・金額を自動減額したりしない。

## 8. 資材・備品（MAT）

- 資材・備品は購入と費用を記録し、残数の在庫管理はしない。
- 資材は梱包用・商品構成用を扱い、購入日・記録順・明細順で選ぶ最新購入単価、またはSKU指定単価を候補にする。
- 販売時に参照購入・単価・使用量・使用原価・確定状態を固定する。追加購入で過去の使用原価を変更しない。
- 追加使用・誤使用訂正は理由と参照関係を付けて追記する。在庫移動・出金を作らない。
- 商品別利益では資材使用原価を配賦し、事業全体では購入費用を計上する。資材購入と使用を二重の事業費用にしない。

## 9. お金・決済（MONEY）

### 9.1 取引と決済

- 業務取引、実際の支払・受取、口座間振替を分離する。未払い・未受取を保持し、分割決済に対応する。
- 通常口座は円建てで部門・申告主体ごとに持ち、開始日・開始残高と保存済み入出金明細から残高を計算する。
- 購入・販売の記録だけで口座残高を増減しない。同時決済を明示した場合は取引と一括して保存する。
- 販路の受取口座・手数料・送料の差引方法は販売保存時の値を使う。
- 元取引の訂正前後を同じ精算系統で追跡し、記録済みの支払・受取・返金を照合して上限を検証する。
- 取消は元記録を保持して反対入出金を追加する。依存する有効な精算がある記録の直接取消を拒否する。

### 9.2 振替・カード・私用資金

- 振替元・先の入出金一組と手数料を同時保存する。手数料は独立した費用とする。
- 通常口座とクレジットカードを明示的に分類する。名称から自動分類せず、種別変更でも元の金額と明細を保持する。
- カードは一括利用・返金・銀行引落を扱う。開始未払額は非負で入力し、未払額を正表示、返金超過を返金・預け残高として表示する。分割・リボは対象外。
- 私用口座・個人カードは事業分だけを記録する。私用全体の残高を登録しない。
- 私用から事業への入金、事業から私用への送金、カード引落は利益へ含めない。

### 9.3 本人立替

- 本人は選択中の申告主体に対応する人であり、入力担当者ではない。
- ワークスペース・部門・申告主体ごとの内部精算台帳を使い、通常口座選択と残高一覧から除外する。通常振替で内部区分へ直接アクセスさせない。
- 元支払・返金・精算と充当内訳を不変の行で保持する。取消は反対記録の有効性から判定する。
- 精算は支払日・記録順・IDの古い順に充当し、部分精算・一括精算の内訳を保存前に表示する。
- 精算日までの未精算額を上限とし、将来日付の既存充当も予約済みとして過大・遡及二重精算を拒否する。
- 元購入の返金は同じ系統の未精算へ充当し、精算済み分は本人から事業への返金待ちとして残す。過去の充当を自動で付け替えない。
- 翌年度の精算で元年度の費用・元支払を再計上しない。
- 私用資金移動、本人立替精算、差額返金は利益へ含めない。別途記録した手数料は費用として扱う。

### 9.4 その他の費用・収入

- 独自の収支項目を入力中に追加でき、任意で元購入・販売に関連付ける。
- 項目追加だけでは在庫・原価を変えない。販売に関連する再送料・追加費用は商品別利益へ反映する。
- 任意の同時決済も取引と同一トランザクションにする。
- 決済状態は現在有効な記録済み決済から求める。表示期間外・翌年度の決済も照合し、取消済みを除外する。
- 反対収支の対象額は元の実決済額を上限とする。未決済・一部決済・決済済み・差額確認・取消済み・決済不要を区別する。

### 9.5 入出金履歴

- 「入出金履歴」「その他の費用・収入」を各50件で表示し、上下に総件数・範囲・現在ページ・前後操作を置く。日付・記録日時・IDの降順で安定させる。
- 初期期間は選択年度全体、口座はすべて。条件変更・タブ切替は1ページ目へ戻り、タブ切替では期間・口座を引き継ぐ。
- 通常行に日付、具体的な内容、口座の動き、金額を表示する。名称は保存時の取引先・SKU等のスナップショットを使い、取得不能なら日本語の取引種類を使う。
- 通常口座の符号・金額は、手数料を含むその口座の保存済み全明細をBigIntで合算して求める。
- 全口座の振替は金額・方向・手数料を示す。振替9,800円・手数料200円なら元口座−10,000円、先口座＋9,800円とする。
- カードは利用・引落・返金、私用資金は本人立替・本人受取を併記する。本人立替精算は事業口座の出金として示す。
- 行内詳細はクリック・Enter・Spaceで同時に1件だけ展開する。明細・手数料・メモ・関連取引・取消状態を表示し、閉じると要約へフォーカスを戻す。
- 閉じたPC行の最小高さは80pxとし、長い名称を折り返す。スマホでは内容・金額を上段、日付・口座を下段へ置く。
- 取消入力は明示的に開き、理由・日付を入力する。保存中・結果不明は行の開閉を止め、入力と照会操作を保持する。
- 詳細往復・保存・取消・結果照会後は元の条件・ページ・位置へ戻る。保存後の復帰先は同じアプリのお金一覧に限定する。
- 件数とページを読み取りトランザクションで取得し、ページ内の関連情報はまとめて照合する。境界外のIDから位置や名称を取得しない。
- 表示位置はワークスペース・部門・申告主体・入力者・年度で分け、残高・本人立替には計算基準日を示す。

## 10. 管理集計（REPORT）

- 商品別利益は販売金額、確認済み費用、返金・返還、有効な管理原価、資材使用原価、関連追加費用を反映する。
- 事業集計は購入済み資材の使用額を再加算しない。口座振替・カード引落・私用資金・立替精算を売上や利益に混ぜない。
- 完了日と有効日を日本時間で集計し、返品・原価訂正を元販売の管理集計へ反映する。
- 不明・暫定の費用や原価を確定利益へ混ぜず、管理利益と実際の口座残高を区別する。

## 11. 共通保存・競合・通信（SAVE）

- 入力検証、Origin確認、認証、入力先、年度、版、共通部門ロック、監査を更新処理に適用する。
- 保存要求はUUIDの冪等キー、対象版、入力先、内容識別値、必要な原価確認版を持つ。同キー・同内容は同じ結果、同キー・別内容は拒否する。
- 在庫・販売・決済等の複合更新、要求結果、監査をDBトランザクションで確定する。共通部門ロックと在庫版の更新を維持する。
- ワークスペース設定、部門ID順の在庫、対象行の順でロックする。年度ロック・年度別割当も共通順序を守る。
- プレビューと業務確定を分ける。プレビューで一時作成した記録はロールバックし、確認操作だけで業務更新しない。
- 確定待ち・処理中・保存済み・確認修正必要・取消済み・結果不明を区別する。結果不明を未保存と断定しない。
- 応答欠落時は元の要求を照会し、明示的な再送・取消へ進む。未送信取消は墓標を保存して遅延要求を止める。
- 途中保存にも要求IDと版を使う。競合では入力開始時・現在保存・手元入力を比較し、基準を変更しない。
- 選び直しは元基準・元入力・理由を退避して新下書きを作るだけとする。選択や再開だけで保存・入庫・取消・返品を確定しない。自動マージしない。
- 未解決の確定要求は先に照会・取消する。通信復帰で業務確定を自動再実行しない。
- オフラインでは更新しない。PWAは静的外枠のみを保持し、認証済み業務データ・更新要求をキャッシュしない。

## 12. 永続データ・技術・運用（DATA）

- テーブル名は英語snake_case、主キーはUUID。日時はUTC、画面はAsia/Tokyo。
- 円額は整数円／BigInt、換算・重量・容積・単価・配分はDecimal。JavaScript numberで金額計算しない。JSON境界の金額は文字列にする。
- 確定取引・移動・消費・充当を物理削除・上書きしない。訂正・取消・反対処理と監査を使う。設定は無効化する。
- PrismaスキーマとマイグレーションSQLを同時に管理する。強化FK・トリガー等を自動同期で失わず、追加マイグレーションを使う。
- Next.js App Router、TypeScript、React、PostgreSQL、Prisma、Zod、Decimal.js、Vitest、Playwright、Docker Composeを使う。正確な依存版はpackage.json・pnpm-lock.yamlを参照する。
- 初回アカウントはCLIで作成する。パスワードは非表示入力し、Argon2idハッシュを保存する。Cookieは不透明トークン、DBセッションはそのハッシュを保持する。
- アプリ内認証を外部アクセス制御で代替しない。正式利用はHTTPS・Secure Cookieを使い、DBポートを外部公開しない。
- 認証情報、Cookie、パスワード、秘密鍵をリポジトリ・ログ・監査JSONへ含めない。
- バックアップはPostgreSQLカスタム形式をageの公開鍵で暗号化し、日次14日・月次12か月を保持して別保存先へ複製する。成功・失敗をDB外の状態記録から表示する。
- 復元は別の空DBで検証する。更新前にバックアップし、失敗時は更新を停止する。
- 初回正式利用はこのWindows PCと同一LANに限定する。専用Composeプロジェクト・空DB・認証情報・鍵・保存先を使い、通常DBと検証DBを引き継がない。HTTPSの入口以外をLANへ公開せず、PC・スマホで専用ルート証明書を信頼して使用する。
- 正式利用の初回構築と更新を分け、配備対象のコミットと作業ツリー・DBを確認する。更新・復元照合中はアプリを停止し、未完了の運用操作がある場合は自動起動しない。再起動時にマイグレーションや業務確定を自動実行しない。
- バックアップはDB起動待ちと失敗後の5分間隔の再試行を行う。チェックサムはファイル名を基準にして複製先でも検証できるようにし、暗号化ファイルの複製一致とOneDriveの同期完了を区別する。
- 通常DB・スマホDB・検証DBを区別し、初期化・削除・自動変換しない。スキーマ変更と正式利用への適用は別に扱う。

## 13. 確認と完了判定（ACCEPT）

変更単位で型・単体／DB統合・lint・build・対象PC／スマホ幅E2Eを確認してから次へ進む。資料変更はフォーマット・参照・仕様の整合性を確認する。

以下を別々に記録する。

1. 対象機能の実装と、確認したコード・DB制約。
2. 自動試験の対象、実行日、環境、成功・失敗・スキップ。
3. 実機のタッチ、キーボード、アプリ切替、通信復帰、人の入力時間の受入。
4. 実際の書類書式での取込確認、空DB導入・暗号化復元、正式利用への適用。

試験失敗・環境エラー・未実行を成功と扱わない。詳細は [検証状況](../docs/validation.md)、レビューの観点と操作例は [レビュー手順](../docs/review-guide.md) を参照する。
